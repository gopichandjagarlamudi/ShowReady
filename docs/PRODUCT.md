# Product Workflows

## Product Summary

ShowReady is designed for agents who want to qualify leads before spending time on showings. The app separates public intake from private agent operations: buyers or renters answer a branded invite flow, ShowReady scores the submission, then the agent reviews and manages the lead inside a protected workspace.

## Core Product Objects

### Agent

- authenticated through Supabase Auth
- represented in `public.agents`
- configured through `agent_settings` and `question_templates`

### Invite

- generated by an agent
- represented in `public.invites`
- can move through `generated`, `opened`, `converted`, and `expired`

### Lead

- created from an invite-backed intake conversion
- represented in `public.leads`
- collects scored answers, summary text, recommendation, review state, and pipeline stage

### Appointment

- tied to a lead and an agent
- stores status, date/time, notes, and one or more showing addresses

## Public Workflow

### 1. Invite generation

- The agent generates an invite from `/dashboard`
- The app stores an invite token and draft payload
- The resulting magic link points to `/intake/[token]`

### 2. Intake start

- The prospect opens the invite link
- ShowReady resolves the token, agent branding, and intake configuration
- The form adapts to `sale` or `rental` intake type

### 3. Autosave

- The browser sends draft updates to `/api/intake/[token]/autosave`
- The server validates mutability before updating persisted draft state
- The public browser never receives service-role credentials

### 4. Submit

- The browser posts the final intake to `/api/intake/[token]/submit`
- The server asserts required answers, flattens the payload, scores the submission, stores lead answers, stores the score row, updates the lead, and converts the invite

### 5. Completion

- The prospect lands on `/intake/[token]/complete`
- The lead is now visible in the private agent workspace

## Private Agent Workflow

### Authentication

- Agents can sign in with email/password
- Agents can sign up with email/password
- Google OAuth is supported when configured in Supabase
- Protected routes are enforced in `proxy.ts`

### Onboarding

- New agents are redirected to `/settings?onboarding=1`
- They configure name, brokerage, branding, threshold, notification preference, intake type, and custom questions
- Runtime scaffolding backfills missing rows if the auth trigger did not create them

### Dashboard

The dashboard is the operator home screen.

It includes:

- pipeline pulse metrics
- average score and total leads
- invite launcher
- generated-link panel
- recent leads list

### New leads review

- Newly submitted leads land in `/new-leads`
- The app computes a suggested stage from the score and recommendation
- The agent must review and either confirm or override that suggestion
- Only after review does the lead enter the active pipeline

### Active pipeline

`/leads` is the primary lead-management workspace.

Active tabs:

- `ready_to_show`
- `appointment_booked`
- `nurture`
- `hold`

Outcome tabs:

- `closed_won`
- `closed_lost`
- `archived`

Behavior notes:

- active and outcome sections are split into separate tab rails
- cards keep persistent footer actions
- bulk actions remain hidden until at least one lead is selected
- the `new` stage is intentionally handled in `/new-leads`, not as an active board column

### Lead detail

`/leads/[leadId]` is the single-lead operational view.

It provides:

- intake answers
- score and recommendation context
- review state
- stage controls
- appointment context and related actions

### Appointments

`/appointments` organizes appointments into:

- scheduled
- completed
- cancelled

Agents can:

- create a new appointment for an eligible lead
- edit an existing appointment
- update appointment status
- manage showing addresses and notes

## Scoring Model

The scoring engine is deterministic, not AI-generated.

It evaluates:

- urgency
- finances
- clarity
- readiness
- fit

Outputs:

- total score
- score breakdown
- recommendation: `show`, `nurture`, or `hold`
- generated summary
- next-action guidance

The score engine lives in `packages/scoring/src/index.ts` and is treated as a deliberate product contract.

## Sale vs Rental Intake

ShowReady supports two intake types:

- `sale`
- `rental`

The type controls:

- core questions
- optional questions
- template defaults
- intent mapping
- score-path logic

Shared product contracts live in `packages/types/src/index.ts`.

## Notifications And Analytics

### Notifications

- Resend is optional
- notification send paths are server-side
- the app can run without notification credentials

### Analytics

- PostHog forwarding is optional
- server event hooks exist for auth, onboarding, invite creation, appointments, and lead changes

## Current Operational Assumptions

- Supabase is required for the active runtime
- invite persistence and intake conversion are server-owned flows
- agent-facing data should use user-scoped Supabase clients
- Realtime updates are wired around the `leads` table

## Typical Happy Path

1. Agent signs in
2. Agent generates an invite from the dashboard
3. Prospect opens the invite and completes the intake
4. ShowReady scores the submission and creates the lead
5. Agent reviews the new lead in `/new-leads`
6. Agent moves the reviewed lead into an active stage
7. Agent schedules an appointment if the lead is ready
8. Lead eventually moves to a closed or archived outcome
